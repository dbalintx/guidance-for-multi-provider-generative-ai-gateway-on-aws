# Deploying into a fresh AWS account — prerequisites and gotchas

Working notes from deploying into a brand-new, never-bootstrapped account, to be folded into the setup documentation. Record every prerequisite here the moment it is hit, even when a script automates it.

## Known upfront (to be verified on the real account)

- **Terraform state bootstrap.** Terraform has no `cdk bootstrap` equivalent; state needs a versioned, private S3 bucket with locking before the first `terraform init`. `deploy/deploy.sh` creates it on first run — that creation *is* the bootstrap step: bucket `litellm-gateway-tfstate-<account-id>-<region>` (override with `TF_STATE_BUCKET`), versioning on, SSE-S3 encryption, all public access blocked, object ownership `BucketOwnerEnforced`, a TLS-only bucket policy, native S3 state locking (`use_lockfile=true`, no DynamoDB table). Terraform >= 1.11 is required (write-only arguments keep the generated secrets out of state). Each deployment's state lives under `<deployment_name>/` in the bucket, and the scripts refuse a bucket of that name owned by another account (`--expected-bucket-owner`). The caller needs `s3:CreateBucket`, `s3:PutBucketVersioning`, `s3:PutEncryptionConfiguration`, `s3:PutBucketPublicAccessBlock`, `s3:PutBucketOwnershipControls`, `s3:PutBucketPolicy`, `s3:ListBucket`/`HeadBucket`, object read/write on the bucket, and `sts:GetCallerIdentity` (used to derive the bucket name).
- **Bedrock model access.** A fresh account has access to no foundation models. Model access must be requested/enabled (console → Bedrock → Model access) in the target region before any invocation can succeed; some vendors require a use-case form. Without it, the gateway deploys fine and every model call fails.
- **Service-linked roles.** First-ever use of ECS, ElastiCache, RDS, ELB or Client VPN in an account creates service-linked roles implicitly; creation requires `iam:CreateServiceLinkedRole`.
- **Default quotas.** Possible first-deploy blockers: 5 Elastic IPs/region (NAT), VPCs/region (5), ALBs/region, Fargate on-demand vCPU quota.
- **Region enablement.** Opt-in regions must be enabled on the account first.
- **Customer KMS key policy (when `kms_key_arn` is set).** The foundation passes the key ARN to RDS, ElastiCache, Secrets Manager, CloudWatch Logs and S3 but does not manage the key's policy. The key policy must allow those services (and the deploying principal) to use the key — in particular CloudWatch Logs needs `kms:Encrypt*`/`kms:Decrypt*`/`kms:GenerateDataKey*`/`kms:Describe*` granted to `logs.<region>.amazonaws.com`, or the flow-log group creation fails with `AccessDeniedException`; RDS/ElastiCache fail at create time with a KMS error if the key is unusable. With `kms_key_arn = null` everything uses AWS-managed keys and no key policy work is needed.
- **RDS Enhanced Monitoring / Performance Insights.** The foundation creates the monitoring role itself (`<deployment>-rds-monitoring`), but the deploying principal needs `iam:CreateRole`, `iam:AttachRolePolicy` and `iam:PassRole` for it. Performance Insights must be available for the chosen instance class (it is for `db.t4g.large`, the default).
- **Availability Zones.** The created VPC takes the first two available AZs. Accounts whose default region has fewer than two usable AZs (rare; some opt-in regions or capacity-restricted AZs) cannot deploy; bring-your-own-VPC validation enforces two AZs as well.
- **ElastiCache auth + TLS from clients.** Redis requires TLS (`transit_encryption_mode = "required"`) and an auth token. Any client beyond the gateway (for example something admitted via `extra_data_ingress_cidrs`) must connect with `rediss://` and the token from the Redis auth secret — plain `redis://` connections are refused at the protocol level, which looks like a timeout from naive clients.
- **The gateway image comes from ghcr.io, so tasks need outbound internet.** The official image `ghcr.io/berriai/litellm` is pulled by Fargate through the task subnets' route to the internet (the created VPC's NAT gateway, or your own egress). In no-internet mode (`disable_outbound_network_access = true`), or in a bring-your-own VPC without egress, tasks fail with `CannotPullContainerError` — unless the image is copied into the account's ECR first (`deploy/mirror-image.sh`) and `image_uri` points at the copy, which the ECR interface endpoints then serve (created automatically in no-internet mode; in a bring-your-own VPC set `create_vpc_endpoints_in_existing_vpc` and `create_interface_endpoints`, or provide them). The image pull does not go through `HTTPS_PROXY`, so `egress_proxy_configured` does not cover it either.
- **WAF logging needs CloudWatch Logs delivery permissions (public mode).** The app sends WAF logs to the `aws-waf-logs-<deployment>` log group. When logging is enabled, AWS adds a CloudWatch Logs resource policy for log delivery, so the deploying principal needs `logs:CreateLogDelivery`, `logs:PutResourcePolicy`, `logs:DescribeResourcePolicies` and `logs:DescribeLogGroups` in addition to the WAF permissions. With `kms_key_arn` set, the key policy must also allow CloudWatch Logs for that log group (see the customer KMS key entry).
- **The machine running Terraform needs the AWS CLI for the app apply.** The app apply uploads the rendered LiteLLM config (`deploy/put-config.sh`, `s3:PutObject` on the config bucket, plus `kms:GenerateDataKey` with a customer key) and runs the schema migration task (`deploy/run-migration.sh`: `ecs:RunTask`, `ecs:DescribeTasks`, `ecs:StopTask`, `iam:PassRole` on the two task roles), both through the AWS CLI with the deploying credentials.
- **ALB access logs use the log-delivery service principal.** The access-log bucket policy grants `logdelivery.elasticloadbalancing.amazonaws.com`, which regions launched after August 2022 require (they have no regional ELB account). AWS documents it for those regions; whether every older region accepts it in place of the regional ELB account was not verified here. If ALB creation fails with `Access Denied for bucket` in an older region, add that region's ELB account principal to the policy.
- **Demo Client VPN certificates must be RSA 1024 or 2048.** Client VPN rejects other key types and sizes (ECDSA, RSA 4096) at import or endpoint creation. `deploy/setup-vpn.sh certs` generates RSA 2048.
- **Demo Client VPN is billed by the hour.** Each subnet association is billed for every hour the endpoint exists, plus each connected client per hour. The foundation associates one private subnet, which is enough to reach the whole VPC. Set `create_vpn = false` and deploy again once the trial is over.
- **Demo Client VPN availability delay.** The apply returns before the endpoint is usable. Clients can connect only once the endpoint state is `available`, which can take several minutes after `terraform apply` completes. Run `deploy/setup-vpn.sh profile` after that.

## Limitations

- **A customer KMS key also encrypts the alarm topic.** With `kms_key_arn` set, the app's observability module encrypts the alarm SNS topic with that key instead of creating a dedicated one. CloudWatch can publish to the topic only if the key policy grants `cloudwatch.amazonaws.com` `kms:Decrypt` and `kms:GenerateDataKey*`. Without that grant the deploy succeeds and the alarms change state, but no notification is delivered. Add this grant to the key-policy requirements above. With `kms_key_arn = null` the module creates a key with the right policy.
